# Mac 사진 앱 자동화

사진 앱의 **`Reframe` 앨범**을 원본으로 사용합니다. 새 테스트를 시작하면 **`Reframe-YYYYMMDD-HHMMSS-밀리초`** 작업 앨범과 독립된 사진 사본을 한 번에 만들고, 사본에 Reframe 적용 → 프리뷰·결과 캡처 → JPEG 저장을 실행합니다. **원본 `Reframe`은 편집하지 않으며, 작업 앨범과 생성 결과는 보존합니다.**

## Reframe 앨범으로 시작하기

1. 사진 앱에 **`Reframe`**이라는 앨범을 만들고 처리할 사진을 넣습니다. 같은 이름의 앨범이 여러 개이면 중단합니다.
2. 최초 환경·권한 설정 후 **`Mac 사진 자동화 1장 테스트.command`**를 실행합니다. 앨범의 사진 전체를 독립된 사본으로 복사하고, 그중 한 장만 편집합니다.
3. 결과가 맞으면 **`Mac 사진 자동화 시작.command`** 또는 **`Mac 사진 자동화 이어하기.command`**로 같은 작업 앨범의 나머지를 처리합니다. 완료한 사진은 건너뜁니다.
4. 전체 완료 후 다시 실행하면 완료 안내만 표시합니다. **`Mac 사진 자동화 새 테스트.command`**는 새 날짜시간 사본을 만들어 한 장을 테스트합니다. CLI에서는 아래의 `--new-run`을 사용합니다.

```bash
node scripts/run.mjs plan               # Reframe 원본 목록 조회만. 복사·편집 없음
node scripts/run.mjs run --limit 1     # 최초 사본 생성 + 다음 사진 한 장 처리
node scripts/run.mjs resume            # 같은 사본의 나머지 처리
node scripts/run.mjs run --new-run --limit 1  # 새 날짜시간 사본으로 새 테스트
```

앨범 ID나 시작할 사진을 직접 지정할 필요가 없습니다. 복사는 원본 사진의 파일 데이터를 읽어 **새 사진 ID**로 생성하는 방식입니다. 단순히 기존 사진을 다른 앨범에 추가하는 방식이 아니므로 사본의 편집이 원본으로 전파되지 않습니다. iCloud 사진을 쓰면 새 사본과 편집 결과는 동기화될 수 있습니다.

복사 대상은 **일반 정지 이미지의 편집 전 원본 파일**입니다. 0.3.1부터 기존 편집 사진도 원본 파일 기준으로 사본을 만들며, 원본 앨범의 편집 상태는 그대로 둡니다. 동영상·Live Photo·지원하지 않는 이미지는 편집이나 앨범 생성 전에 중단합니다. 사진 파일 안의 메타데이터는 유지하지만 Photos의 즐겨찾기·제목·키워드 등 보관함 속성과 편집 이력을 복제하는 기능은 아닙니다.

중간에 중단해도 같은 사본을 이어합니다. 복사 응답이 유실된 경우에는 중복 생성을 막기 위해 자동으로 복사를 반복하지 않습니다. 작업 사본의 구성 변경도 중단합니다. `Reframe`에 나중에 추가한 사진은 기존 작업에 끼워 넣지 않으며, 다음 `--new-run`에 포함됩니다.

0.3.0부터 배포 기본 설정은 `"albumName": "Reframe"`입니다. 이전 `config.json`에 이 항목이 없을 때도 Reframe을 사용합니다. `"albumName": null`로 설정하면 이전 InputImages 방식을 명시적으로 유지할 수 있습니다. 두 모드의 이어하기 기록은 분리됩니다.

## 준비

- Reframe을 지원하는 macOS 27의 사진 앱과 Apple Intelligence 설정이 필요합니다. 실제 화면에 `편집 → 도구 → 프레임 재설정`이 있어야 합니다. 언어·지역·사용량에 따라 기능 사용이 제한될 수 있습니다.
- Node.js **22.12 이상**과 **Command Line Tools**가 필요합니다. 전체 Xcode 앱, Apple 개발자 계정 로그인, 개발자 인증서는 기본 실행에 필요하지 않습니다. Node.js 26.9.0도 허용하며, 22 버전으로 낮출 필요가 없습니다. npm 패키지 의존성은 없습니다.
- 작업할 보관함을 **시스템 사진 보관함**으로 지정하고 사진 앱에서 열어 둡니다. PhotoKit이 읽는 시스템 보관함과 사진 앱의 항목 ID가 일치하지 않으면 중지합니다.
- 사진 앱은 일반 격자 화면으로 열어 두면 됩니다. 시작할 사진을 미리 크게 열 필요는 없습니다. 자동화가 작업 사진을 열고 전면으로 가져옵니다. 화면 잠금을 해제하고, 처리 중 다른 창을 띄우거나 마우스·키보드로 사진 앱을 조작하지 않습니다.

다음 네 권한은 `Mac 사진 자동화` 도우미에 부여합니다. macOS에 따라 표시 이름이 `MacPhotosBridge`일 수 있습니다.

| 권한 | 용도 |
| --- | --- |
| 손쉬운 사용 | 사진 앱의 버튼·메뉴·드래그 조작 |
| 화면 및 시스템 오디오 기록의 화면 기록 | 사진 앱 창 캡처 |
| 자동화 → 사진 | Apple Events로 사진 앱의 앨범·항목 제어 |
| 사진 → 전체 접근 | 입력 사진 복사·작업 앨범 생성, 사진 ID와 편집 상태 확인·결과 내보내기 |

설정 명령은 도우미의 설정 창을 엽니다. **손쉬운 사용 요청**, **화면 기록 요청**, **사진 전체 접근 요청**, **자동화 → 사진 요청**을 하나씩 눌러 승인합니다. 각 권한 옆의 **설정 열기** 버튼으로 해당 macOS 설정도 바로 열 수 있습니다. 사진 권한은 제한된 사진 선택이 아닌 전체 접근을 허용해야 합니다. 자동화 요청은 사진 앱의 선택 항목을 조회하여 권한을 요청하며 사진을 변경하지 않습니다.

단순 빌드나 백그라운드 실행은 권한을 자동 요청하거나 초기화하지 않습니다. 일반 권한 요청 버튼도 기존 허용 기록을 지우지 않습니다. 권한은 `시스템 설정 → 개인정보 보호 및 보안`에서도 확인할 수 있습니다. 화면 기록 권한 변경 후에는 macOS 안내에 따라 도우미의 **보조 앱 종료** 버튼을 누른 뒤 설정 명령으로 다시 실행해야 할 수 있습니다.

## 처음 환경 설정하기

새 Mac에는 먼저 터미널에서 `xcode-select --install`을 실행해 **Command Line Tools**를 설치합니다. Swift 컴파일러와 macOS SDK가 포함된 별도 패키지이며 전체 Xcode 앱을 설치하는 명령은 아닙니다. 사용 중인 macOS에 맞는 최신 버전을 사용하세요. [Apple 설치 안내](https://developer.apple.com/documentation/xcode/installing-the-command-line-tools).

1. **`Mac 사진 자동화 설정.command`**를 실행합니다. 새 Mac에서는 인증서 없이 로컬 임시 서명(ad hoc)으로 빌드합니다. 도우미가 꺼져 있으면 빌드 후 설정 창을 열고, 이미 실행 중이면 빌드 없이 기존 설정 창을 다시 엽니다.
2. 도우미 설정 창에서 위 네 권한을 **각각 요청**하고 부여합니다. **상태 새로고침**으로 네 항목의 상태를 확인합니다.
3. 앨범 방식은 사진 앱에 **Reframe** 앨범을 준비합니다. 파일 가져오기 방식을 쓸 때만 **`InputImages/`에 처리할 사진 파일을 넣습니다.** 사진 앱은 시스템 사진 보관함의 일반 보기 화면으로 열어 둡니다.
4. 터미널에서 입력 목록과 실행 환경을 확인합니다. 아래 경로는 실제 프로젝트 위치로 바꾸세요.

   ```bash
   cd /path/to/MacGyver/macos-automation
   node scripts/run.mjs plan
   node scripts/run.mjs check
   ```

기본 `plan`은 Reframe 앨범과 사진 목록을 조회합니다. `albumName`이 없는 기본 `plan`은 **파일시스템의 입력 파일과 순서만 조회**합니다. 사진 앱을 열거나 권한을 부여하지 않아도 실행할 수 있으며, 사진을 보관함으로 가져오지 않습니다.

### 화면 기록 요청 창이 뜨지 않을 때

손쉬운 사용을 승인해도 화면 기록은 별도로 승인해야 합니다. **화면 기록 요청**을 누르세요. 이미 허용했거나 이전에 거부한 경우 macOS가 요청 팝업을 다시 표시하지 않을 수 있습니다.

1. **화면 기록 설정 열기**를 눌러 `개인정보 보호 및 보안 → 화면 및 시스템 오디오 기록`을 엽니다.
2. `MacPhotosBridge` 또는 `Mac 사진 자동화`를 켭니다. 목록에 없다면 도우미의 **현재 앱 Finder에서 보기**로 실행 중인 앱 위치를 확인한 뒤, 설정 목록 아래 **+**로 그 `MacPhotosBridge.app`을 추가합니다. 보통 위치는 `macos-automation/build/MacPhotosBridge.app`입니다.
3. 도우미의 **보조 앱 종료**를 누르고 **Mac 사진 자동화 설정.command**를 다시 실행합니다. **상태 새로고침**에서 화면 기록이 허용으로 표시되는지 확인합니다.

추가할 항목은 현재 빌드한 도우미 앱입니다. 화면 기록 목록의 **+**로 앱을 추가하는 절차는 [Apple 화면 기록 권한 안내](https://support.apple.com/guide/mac-help/control-access-to-screen-and-system-audio-recording-mchld6aa7d23/mac)에서도 설명합니다.

### 권한 재등록이 필요한 경우에만 초기화하기

0.2.1부터 새 Mac의 기본 빌드는 다시 인증서 없는 임시 서명입니다. **코드가 바뀌어 재빌드되면 macOS 권한을 다시 승인해야 할 수 있습니다.** 먼저 권한 상태를 확인하고, 문제 없이 동작하면 초기화하지 마세요. 선택적으로 개발자 인증서를 사용하는 기존 Mac은 저장된 같은 인증서를 계속 사용합니다.

0.1.5부터 설정 창의 **이 앱 권한 초기화 후 종료** 버튼으로 이 도우미의 기존 권한 결정을 초기화할 수 있습니다. 새 코드를 적용하려면 먼저 실행 중인 도우미의 **보조 앱 종료**를 누르고 설정 커맨드를 다시 실행해 빌드하세요.

1. 사진 자동화를 종료하고 미완료 편집이 있으면 먼저 복구합니다.
2. 새 설정 창에서 **이 앱 권한 초기화 후 종료**를 누릅니다. 네 권한의 초기화가 모두 성공하면 도우미가 종료됩니다.
3. **Mac 사진 자동화 설정.command**를 다시 실행한 뒤 네 권한 요청 버튼을 하나씩 눌러 승인합니다.
4. 일부 초기화가 실패하면 해당 권한과 오류를 창에 표시합니다. 이 경우 **보조 앱 종료**를 직접 누르고 설정 커맨드로 다시 시작한 뒤 상태를 확인하세요. 앱을 다시 시작하기 전에는 권한을 재요청하지 않습니다.

초기화 대상은 `local.macgyver.photosautomation`의 `Accessibility`, `ScreenCapture`, `Photos`, `AppleEvents` 네 항목으로 고정되어 있습니다. macOS의 `tccutil reset`으로 이 도우미의 승인·거부 기록만 초기화하며, 다른 앱의 권한은 바꾸지 않습니다. **초기화가 새 권한을 자동 승인하지는 않습니다.** 시스템 설정 목록에 표시되는 앱 항목은 남아 있을 수 있으며, 새 요청의 승인과 목록 관리는 macOS에서 처리합니다. [Apple 권한 초기화 안내](https://developer.apple.com/documentation/xcode/resetting-access-to-protected-resources-in-macos).

자동화 실행 중에는 권한 요청과 초기화를 차단합니다. 미완료 편집이 남아 있으면 초기화는 막지만, 복구에 필요한 권한 요청·설정 열기는 허용합니다. 복구 기록을 지우고 초기화를 강행하지 마세요. 빌드할 때마다 초기화하는 방식이 아니라, 재등록이 필요할 때 이 버튼으로 명시적으로 실행하는 방식입니다.

0.1.8에서는 권한 **요청** 버튼을 눌렀을 때 앱이 시스템 설정까지 동시에 열던 동작을 제거했습니다. 요청 후 나타난 macOS 안내창을 먼저 확인하세요. 이전 거부 등으로 안내창이 나오지 않을 때는 옆의 **설정 열기** 버튼을 사용합니다. 사진 접근·자동화 요청도 같은 방식이며, 이미 허용된 권한을 초기화하지 않습니다.

### 입력 사진 준비와 1장 테스트

지원 확장자는 `jpg`, `jpeg`, `png`, `heic`, `heif`, `tif`, `tiff`입니다. `InputImages/` 바로 아래의 파일을 이름순으로 처리하며, 하위 폴더와 동영상은 포함하지 않습니다. 가져오기 단계에서 실제 이미지 데이터가 유효한 단일 프레임 정지 이미지인지도 검사합니다. 확장자가 맞아도 애니메이션·다중 프레임·손상 파일은 처리하지 않습니다.

`plan`으로 대상을 확인한 뒤 처음에는 **`Mac 사진 자동화 1장 테스트.command`**를 실행하거나 아래 명령을 사용합니다. **사진 전체를 한 번에 가져오고, `--limit 1`은 그중 다음 미처리 사진 한 장만 편집합니다.** 다음에 같은 명령을 실행하면 같은 앨범의 다음 사진 한 장을 처리합니다.

```bash
node scripts/run.mjs run --limit 1
```

`.command` 실행 파일은 현재 `PATH`의 Node.js를 우선 사용하고, 사용할 수 없으면 일반적인 설치 경로를 확인합니다. 실행 시 선택한 버전과 경로를 표시하며, 기존 Node.js 설치나 시스템 `PATH`를 변경하지 않습니다. 여러 버전 중 하나를 직접 지정하려면 절대 경로를 설정합니다.

```bash
MACGYVER_NODE='/절대/경로/node' './Mac 사진 자동화 1장 테스트.command'
```

직접 지정한 경로가 실행 불가능하거나 지원 범위 밖이면 다른 Node로 바꾸지 않고 오류를 표시합니다. Finder와 터미널은 `PATH`가 다를 수 있으므로 출력된 실행 경로로 실제 사용 버전을 확인하세요.

최초 실행은 `MacGyver InputImages <ISO 시각>` 이름의 새 앨범을 만들고 폴더 전체를 한 번의 PhotoKit 트랜잭션으로 가져옵니다. `InputImages/`의 파일은 수정하거나 이동하지 않으며 SHA-256으로 확인합니다. **앨범과 편집한 사진은 실행 후에도 남습니다.** iCloud 사진을 사용하면 복사본과 편집도 동기화될 수 있습니다.

0.1.6부터는 검증한 원본 바이트를 전용 임시 파일에 기록해 사진 보관함으로 **파일 복사**합니다. 사진 보관함에서 읽은 원본의 바이트 수와 SHA-256이 입력과 정확히 일치해야 다음 단계로 진행합니다. 임시 파일은 사용자 전용 폴더에 두며 가져오기 요청 완료 후 정리합니다. 앱이 강제 종료된 경우 임시 파일이 도우미 상태 폴더에 남을 수 있습니다.

같은 입력으로 다시 실행하면 같은 작업 앨범과 결과 폴더를 사용하고 완료 사진은 건너뜁니다. **시작** 또는 **이어하기** 커맨드는 남은 전체 사진을 처리합니다. 모든 사진을 처리한 뒤 다시 실행하면 완료 안내만 표시합니다. 입력 파일 목록·내용이 바뀌면 이어하기를 중단합니다. 새 입력이나 새 사본으로 다시 시작할 때만 `npm start -- --new-run`을 사용하세요. 이전 앨범과 결과 폴더는 보존합니다.

드래그·대기 시간을 바꾸려는 경우에만 `config.example.json`을 `config.json`으로 복사해 수정합니다. 설정 파일이 없으면 예제 기본값을 사용합니다.

앨범 복사는 첫 단계입니다. 이후 터미널에 **가져오기 완료 → 사진 열기 → 지정한 사진의 보기 화면 확인 → 원본 사진과 기존 편집 여부 확인 → 편집 시작**이 표시됩니다. 복사한 사진이 보여도 원본 파일 검증이 끝나기 전일 수 있습니다. 더 진행되지 않으면 반복 실행하기 전에 터미널의 마지막 메시지와 오류를 확인하세요. 실행 폴더의 `manifest.json`에는 마지막 도우미 요청(`lastRequest`)과 실패 이유(`error.message`)가 기록됩니다. 이 기록으로 가져오기·사진 열기·원본 검사 중 어느 요청에서 멈췄는지 확인할 수 있습니다.

`대기 시간초과: 구도 변경 후 프레임 재설정 버튼`은 도구 진입 버튼의 `AXTitle`과 생성 화면 버튼의 `AXDescription`을 같은 속성으로 찾던 문제였습니다. 후속 스크립트에서 두 버튼을 분리했습니다. 0.2.0의 전체 가져오기는 새 도우미가 필요하므로 업데이트 후 **보조 앱 종료 → 설정 커맨드 재실행**으로 빌드합니다. 미완료 기록이 있으면 업데이트 빌드 전에 기존 앱으로 `npm run recover`를 실행하세요.

`AX_PRESS_FAILED: AXPress 실패: -25205`가 편집 시작 직후 나타났다면 버튼 동작은 이미 실행됐을 수 있습니다. 0.1.9 이후 스크립트는 **편집·완료 버튼에 한해** 같은 사진·앱·창의 예상 화면 전환을 최대 5초간 확인하고, 확인된 경우 버튼을 다시 누르지 않고 진행합니다. 확인되지 않거나 다른 오류이면 기록을 보존하고 멈춥니다. 이전 실패로 편집 화면이 남았다면 자동 재실행하지 말고, 미저장 내용을 확인해 취소하거나 저장한 뒤 `npm run recover`를 실행하세요.

`사진 보관함의 원본 파일 바이트·SHA-256이 입력 파일과 다릅니다` 오류는 복사 후 검증 단계의 실패이며, 해당 사진의 편집은 아직 시작되지 않은 상태입니다. 0.1.6에서는 가져오기 경로를 수정했고, 불일치 시 기대값·실제값을 오류에 포함합니다. 이전 버전의 `data:` 가져오기 경로가 일부 OS에서 이미지 메타데이터를 바꾸는 사례를 [Apple DTS가 확인했습니다](https://developer.apple.com/forums/thread/845667). 이 답변은 iOS에서의 재현이며, 사용자의 macOS 오류가 같은 원인인지는 실사진 재검증이 필요합니다. 해시 비교를 끄거나 가져오기를 자동 반복하지 않습니다.

가져오기 기능을 업데이트할 때는 **설정 커맨드 → 보조 앱 종료 → 설정 커맨드 재실행(새 도우미 빌드) → 권한 상태 확인 → 1장 테스트** 순서로 진행하세요. 권한 초기화는 필수 단계가 아닙니다. 이전 도우미가 실행 중이면 복사 전에 재빌드 안내를 표시합니다. 이전 실패 기록과 사본은 자동 삭제하지 않습니다.

`Photos AppleScript (-1700)` 또는 `(-1728)`가 사진을 여는 단계에서 발생하면 **0.1.7 이상 도우미로 재빌드**하세요. 사진 앱의 선택 정보에는 다시 조회할 수 없는 내부 앨범 경로가 붙을 수 있습니다. 0.1.7은 그 경로 대신 선택 객체에 들어 있는 전체 사진 ID로 보관함의 같은 사진을 확인합니다. 파일명이 같은 다른 사진으로 대체하지 않습니다. 이 오류로 편집 전에 중단된 실행은 기존 작업 앨범을 지정하는 고급 모드로 같은 사본 한 장을 검사할 수 있습니다.

### 고급 옵션: 기존 사진 앨범 처리

이전 ID 기반 고급 모드를 사용할 때는 `--album-id`를 **명시적으로** 지정합니다. 일반적인 테스트는 위의 Reframe 사본 방식을 사용하세요. 이 모드에서는 앨범 안의 시작할 사진 한 장을 크게 열고, 편집 화면이 아닌 일반 보기 화면에서 시작해야 합니다. 기존 설정 파일의 `albumId` 값은 기본 실행에서 무시합니다.

```bash
node scripts/run.mjs albums
node scripts/run.mjs plan --album-id '<앨범 ID>'
node scripts/run.mjs run --album-id '<앨범 ID>' --limit 1
```

이 고급 `plan`은 기존 앨범을 조회하므로 사진 앱과 관련 권한이 필요합니다. 기존 앨범 모드는 입력 파일을 가져오거나 새 작업 앨범을 만들지 않습니다. 다른 설정 파일은 `--config '/절대/경로/config.json'`으로 지정할 수 있지만, 해당 파일의 `albumName`도 적용됩니다. 이전 ID 기반 모드는 `--album-id`로 지정합니다.

## 실제 처리 순서

1. 기본 모드는 `Reframe`의 사진 ID를 확정하고 날짜시간 앨범에 독립 사본을 만듭니다. 이전 InputImages 모드는 폴더 전체의 입력 목록·순서·해시를 확정하고 한 번에 가져옵니다. PhotoKit이 반환한 정확한 사진 ID 집합이 사진 앱의 작업 앨범과 일치하는지 확인합니다. 이어하기는 기존 앨범과 완료 기록을 확인하고 다음 미처리 사진부터 시작합니다. 입력 파일 순서로 정확한 사진 ID를 열며 표시 정렬 순서에 의존하지 않습니다. 제한 장수는 편집에만 적용합니다.
2. 사진의 기존 편집 여부를 확인합니다. **이미 편집된 사진은 건너뜁니다.**
3. 사진 열기 → 편집 → 도구 → 프레임 재설정으로 진입합니다. 회전·패닝·수평·확대 구도를 읽고, 필요하면 기본 구도로 재설정한 뒤 드래그를 시작합니다. 드래그 전후 구도 값이 실제로 변했는지 확인합니다.
4. 프리뷰를 조작할 준비가 되었는지 확인합니다.
5. 프리뷰 중심에서 왼쪽 아래 45도 방향으로 드래그합니다. 기본 이동 거리는 프리뷰 짧은 변 길이의 절반입니다. **드래그 후 프리뷰 화면을 캡처**합니다.
6. 프레임 재설정을 눌러 결과를 생성합니다. 이때부터 기본 최소 25초를 기다리고, 처리 중 표시가 사라졌으며 저장 버튼이 활성화되었는지 확인합니다. 제한 시간 안에 완료되지 않으면 실패로 기록합니다.
7. **저장 전에 결과 화면을 캡처**한 뒤 저장/완료를 누릅니다.
8. 저장된 편집 결과를 전체 크기 JPEG로 내보냅니다. 파일 크기·해시와 이미지 전체 디코딩을 검증합니다.
9. JPEG 검증과 사진 앱의 편집 결과 유지 여부를 확인합니다. **원본으로 복귀하지 않습니다.** 완료 기록을 남기고 다음 사진으로 이동합니다.

확정한 목록을 모두 처리하면 자동으로 종료합니다. Reframe 복사 모드는 일반 정지 이미지의 원본 파일을 복사합니다. 기존 앨범 모드에서는 이미 편집된 사진과 동영상을 건너뛴 항목으로 기록합니다.

화면 캡처는 사진 앱 **창 전체**를 저장하므로 도구 모음 등 UI가 포함됩니다. 고해상도 사진 결과는 별도 `<원본파일명>-result.jpg`입니다. 창 캡처와 JPEG는 용도가 다릅니다.

기본 모드는 Reframe의 독립 사본을 편집하며 원본 앨범의 사진은 그대로 둡니다. InputImages 모드도 폴더 원본을 변경하지 않습니다. 기존 앨범 모드도 새 작업에서는 결과를 유지하고, 이미 편집된 사진은 건너뜁니다. 기존 앨범의 편집은 같은 사진이 들어 있는 다른 앨범과 iCloud 사진에도 반영될 수 있습니다.

## 실행·중지·복구

### 설정 창을 다시 열기

`설정 창 숨기기`나 빨간 닫기 버튼은 창만 숨깁니다. 보조 앱은 계속 실행되며 아래 방법으로 설정 창을 다시 열 수 있습니다.

- **Dock의 Mac 사진 자동화 아이콘 클릭**
- **⌘Tab으로 Mac 사진 자동화 선택 후 ⌘,**
- 메뉴 막대의 **사진 자동화 → 설정 창 열기**
- Finder에서 **MacPhotosBridge.app** 다시 실행
- **Mac 사진 자동화 설정.command** 다시 실행

완전히 종료하려면 설정 창이나 메뉴 막대의 **보조 앱 종료**를 사용합니다. 자동화에서 도우미를 호출할 때는 설정 창을 띄우지 않도록 별도로 처리합니다.

0.2.1부터 설정 창을 한 번 열면 Dock과 ⌘Tab에 앱이 표시됩니다. 창을 숨기거나 닫아도 Dock 아이콘은 남습니다. 자동화가 설정 창 없이 처음 시작한 경우에만 보조 앱 모드를 사용합니다.

도우미의 Swift 코드가 바뀐 업데이트를 적용할 때는 설정 커맨드로 기존 창을 열고 **보조 앱 종료**를 누른 다음 설정 커맨드를 다시 실행하세요. 실행 중에는 기존 앱의 창을 열 뿐 다시 빌드하지 않습니다. 미완료 편집 기록이 있으면 기존 앱을 열어 복구부터 진행하도록 합니다. JavaScript만 바뀐 업데이트는 다음 스크립트 실행부터 적용되므로 도우미 재빌드나 권한 초기화가 필요하지 않습니다.

| 파일 | 동작 |
| --- | --- |
| `Mac 사진 자동화 설정.command` | 실행 중이면 설정 창 다시 열기, 종료 상태이면 빌드 후 설정 |
| `Mac 사진 자동화 1장 테스트.command` | 최초에는 전체 가져오기, 다음 미처리 사진 한 장 편집 후 종료 |
| `Mac 사진 자동화 시작.command` | 최초에는 전체 가져오기, 기존 작업이 있으면 남은 사진 이어하기 |
| `Mac 사진 자동화 이어하기.command` | 기록된 작업 앨범의 남은 사진 처리 |
| `Mac 사진 자동화 중지.command` | 진행 중인 작업에 중지 요청 |
| `Mac 사진 자동화 복구.command` | 미완료 편집 기록을 기준으로 복구 |

중지는 즉시 프로세스를 강제 종료하는 명령이 아닙니다. 편집 도중 중단되면 `artifacts/pending-edit.json`에 복구할 사진과 단계가 남습니다. 다음 사진으로 넘어가기 전에 `recover`로 이 상태를 처리합니다. 이 기록이 남아 있으면 앱을 다시 빌드하지 않습니다. 기록 파일을 직접 지우거나 사진을 수동으로 바꾼 뒤 이어서 실행하지 마세요.

가져오기 요청 중에는 현재 요청이 끝날 때까지 기다립니다. 전체 가져오기와 검증이 완료된 후 중지하면 같은 앨범으로 이어갈 기록이 남습니다. 오류·강제 종료로 완료 여부가 불분명하면 `import.json`과 도우미 기록을 보존하고 자동 재가져오기를 차단합니다. **`recover`는 미완료 사진 편집만 복구합니다.** 완료 여부가 불분명한 가져오기는 기록과 앨범을 확인해야 하며, 명시적인 `--new-run`은 이전 앨범을 남기고 새 복사본을 만듭니다.

```bash
node scripts/run.mjs stop
node scripts/run.mjs recover
node scripts/run.mjs resume          # 같은 앨범의 남은 사진
node scripts/run.mjs resume --limit 1 # 다음 사진 한 장
node scripts/run.mjs run --new-run    # 명시적으로 새 앨범 생성
```

내보내기가 실패해도 사진 앱의 편집 결과와 미완료 기록을 보존합니다. 복구는 기록된 사진의 JPEG 저장과 편집 결과 유지 여부를 확인합니다. 저장되지 않은 초안을 취소해 복구한 사진은 이어하기에서 다시 처리합니다. **0.2.0 이전 version 1 미완료 기록만 당시 정책에 따라 JPEG 검증 후 원본 복귀를 완료합니다.** 전원이 꺼지거나 앱이 종료되어도 기록으로 미완료 사진을 식별합니다.

복구 실행에서도 “npm run recover를 실행하세요”가 다시 표시되는 이전 버전의 안내는 공통 오류 처리에서 잘못 출력한 문구입니다. 수정판은 **복구할 사진·중단 단계 → 실제 실패 이유**를 표시하고, `manifest.json`의 `recovery.error`와 현재 복구 요청을 기록합니다. 기록을 지우거나 복구를 반복하는 것으로 원인이 해결되지는 않습니다. 복구 창의 실제 오류를 확인하세요. 이 안내 변경은 JavaScript만 수정하므로 도우미 재빌드·권한 초기화가 필요하지 않습니다.

복구를 시작할 때 일반 편집 화면이 남아 있으면 미저장 변경 내용을 구분할 수 없어 멈춥니다. 자동화가 만든 결과라면 `완료`로 저장하고, 불필요한 초안이면 취소하여 일반 사진 보기 화면으로 돌아온 뒤 복구를 다시 실행하세요. 복구는 기록된 사진 한 장만 처리하고 종료합니다.

## 저장 위치와 점검 명령

결과는 `artifacts/photos-<ISO 시각>/` 실행 폴더에 모아서 저장합니다. 사진별 하위 폴더를 만들지 않습니다. 각 파일명은 원본 파일명의 확장자를 뺀 이름으로 시작하며, 중복 이름은 구분합니다.

- `<원본파일명>-preview-capture.png`: 드래그 후, 생성 전 프리뷰 창
- `<원본파일명>-result-capture.png`: 생성 후, 저장 전 결과 창
- `<원본파일명>-result.jpg`: 저장한 편집 결과의 전체 크기 JPEG
- `plan.json`: 확정한 입력·앨범·사진 ID와 처리 순서
- `import.json`: 입력 원본과 가져오기 진행·결과 기록
- `manifest.json`: 사진별 처리 결과와 실행 상태
- `.metadata/`: 도우미 요청 등 복구·검증용 세부 기록

`artifacts/input-batch.json`은 현재 이어갈 작업 폴더를 가리킵니다. 이어할 때 같은 결과 폴더에 저장하며 기존 캡처와 JPEG는 덮어쓰지 않습니다. 중단 후 같은 사진을 다시 처리하면 파일명에 `-002` 같은 구분 번호를 붙입니다.

입력 사진, 화면과 사진이 담긴 산출물 및 로그는 개인 자료입니다. `InputImages/`의 실제 사진과 `artifacts/`, `logs/`, `config.json`은 Git에서 제외합니다. 도우미 IPC 파일과 가져오기 기록은 사용자 전용 권한(`0700`)의 `~/Library/Application Support/MacGyverMacPhotos/`에 둡니다. 기본 실행은 이 고정 경로를 사용하며, 도우미는 필요한 경우 `--ipc-root`로 별도 절대 경로를 지정할 수 있습니다.

```bash
node scripts/run.mjs check     # 실행 환경과 권한 점검
node scripts/run.mjs inspect   # 현재 UI 상태 확인
node scripts/run.mjs albums    # 기존 앨범을 쓰는 고급 모드용 ID 목록
node scripts/run.mjs plan      # Reframe 원본 목록 조회. 복사·편집 없음
```

## 도우미 빌드

```bash
npm run build
```

`native/*.swift`를 Swift 5 언어 모드, macOS 15.2 배포 대상으로 빌드합니다. Reframe 동작에는 macOS 27이 필요합니다. 결과 앱은 `build/MacPhotosBridge.app`, 빌드 로그는 `logs/build.log`입니다. 실행 시 자동으로 다시 빌드하지 않습니다. 소스와 서명 설정이 같고 기존 서명이 유효하면 빌드를 건너뜁니다.

`npm run build`는 실행 중인 `MacPhotosBridge`를 덮어쓰지 않습니다. 설정 창이 숨겨져 있다면 **설정 커맨드를 실행해 창을 다시 열고**, **보조 앱 종료**를 누른 뒤 설정 커맨드를 다시 실행하세요. 앱을 교체한 뒤에는 새 도우미를 시작해야 변경 사항이 반영됩니다. 빌드 스크립트가 실행 중인 도우미를 자동으로 종료하지 않습니다.

**0.2.1의 새 Mac 기본값은 임시 서명(ad hoc)**입니다. 인증서나 Xcode 계정을 확인하지 않습니다. `xcode-select --install`로 설치한 Command Line Tools의 `swiftc`와 macOS SDK로 빌드할 수 있습니다. 소스를 내려받아 빌드하는 방식이므로 컴파일 도구 자체는 필요합니다. 도구가 없으면 설치 명령을 안내하며 자동 설치하지 않습니다.

개발자 인증서 사용은 **선택 사항**입니다. 기존에 인증서 사용 설정을 저장한 Mac은 승인 상태를 불필요하게 바꾸지 않도록 같은 인증서를 계속 사용합니다. 이 설정은 `~/Library/Application Support/MacGyverMacPhotos/signing.json`에 있으며 새 Mac으로 배포하지 않습니다. 저장된 인증서가 만료되거나 없어졌을 때만 오류를 표시합니다.

이미 보유한 **Apple Development** 또는 **Developer ID Application** 인증서를 사용하려면 아래처럼 명시합니다. 새 Mac의 일반 설치에서는 이 과정을 건너뜁니다.

```bash
security find-identity -v -p codesigning
MACOS_SIGNING_IDENTITY='<사용할 인증서의 SHA-1 전체 값>' npm run build
# 다음부터 지정할 필요 없음
npm run build
```

앱의 Bundle ID는 `local.macgyver.photosautomation`으로 고정합니다. 같은 인증서·서명 식별 조건·앱 경로를 유지하여 재빌드에 따른 권한 재등록을 줄입니다. 최초 임시 서명에서 전환할 때, 인증서를 교체하거나 macOS 정책이 변경되었을 때는 재승인이 필요할 수 있습니다. 빌드는 권한을 초기화하거나 자동 승인하지 않습니다. 다른 Mac에는 이 설정이나 개인 키를 복사하지 말고 그 Mac의 인증서를 선택합니다.

앱 버전 간 개인정보 접근의 식별 기준인 designated requirement는 [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)에 설명되어 있습니다. 빌드 검사는 인증서 이름만 비교하지 않고 이 조건도 그대로인지 확인합니다.

인증서 설정이 있는 Mac에서도 이번 빌드만 예전 방식으로 수행하려면 `MACOS_SIGNING_IDENTITY=- npm run build`를 사용합니다. 저장된 인증서 설정을 삭제하거나 덮어쓰지는 않습니다. 새 Mac은 이 옵션 없이도 기본적으로 임시 서명을 사용합니다.

## 검증 범위

0.3.1은 2026-09-21 실제 Reframe 앨범의 20장을 새 날짜시간 앨범의 독립 사본으로 만들고, 첫 사진의 좌하단 드래그·프리뷰 캡처·재생성·결과 캡처·JPEG 저장·편집 보존까지 완료했습니다. JPEG는 1440×1801, 1,955,886바이트이며 전체 디코딩·해시 검증을 통과했습니다. 원본 20장의 사진 ID·원본/현재 이미지 해시·기존 편집 여부가 실행 전후 모두 같았고, 원본과 사본의 사진 ID는 겹치지 않았습니다. 기존 편집 원본 2장도 그대로 유지됐습니다. pending과 실행 기록은 정상 정리됐고 같은 사본의 다음 사진부터 이어할 19장 기록이 남았습니다. **실제 편집은 1장만 검증했으며 나머지 19장 전체의 성공으로 확대하지 않습니다.** 편집 버튼의 -25205 응답은 같은 사진의 편집 전환 확인으로 처리했으며 버튼을 다시 누르지 않았습니다.

0.3.0의 오프라인 185개 검사는 사본 ID 분리·한 번만 복사·이어하기·응답 유실 후 중복 복사 차단 등을 확인했습니다. 0.3.1 변경 후 관련 네이티브 테스트와 실제 빌드·서명·권한 유지도 확인했습니다. 아래 기록은 이전 버전의 검증 범위입니다.

0.2.1은 새 Mac의 기본 서명을 인증서 없는 임시 서명으로 되돌렸습니다. 로컬에서 전체 Xcode 대신 `DEVELOPER_DIR=/Library/Developer/CommandLineTools`를 지정해 모든 네이티브 소스를 실제 컴파일하고 임시 앱의 ad hoc 서명·무결성 검증을 통과했습니다(CLT 27.0, Swift 6.4, macOS SDK 27.0). 새 Mac의 실제 설치·권한 승인까지 검증한 것은 아닙니다.

설정 창의 Dock·⌘Tab 표시와 앱 메뉴도 추가했습니다. 로컬 설치 앱을 0.2.1로 빌드해 설정을 열었을 때 macOS의 일반 앱 활성화 정책(`regular`)인 것, 창을 숨긴 뒤 다시 열리는 것과 앱 메뉴의 설정 항목·새 안내문을 확인했습니다. 현재 Mac은 기존에 저장한 개발자 인증서를 재사용했고 네 권한이 유지됐습니다. 오프라인 검사 **178개**가 통과했습니다. 이번 변경으로 사진 배치를 추가 실행하지는 않았습니다.

### 0.2.0 사진 처리 검증

0.2.0은 같은 인증서 재사용, 전체 일괄 가져오기, 같은 앨범 이어하기, JPEG 내보내기 후 편집 결과 보존을 포함합니다. 로컬 개발자 인증서로 실제 빌드·서명 검증했고 다음 빌드가 저장한 인증서를 사용하는 것을 확인했습니다. 오프라인 검사 **178개**가 통과했습니다. 검사에는 전체 가져오기 후 1장 처리·다음 장 재개·완료 후 중복 복사 방지, 입력 변경·불확실한 가져오기 차단, 완료 기록 저장 실패 시 복구 기록 유지, 네이티브 보존 원장과 이전 원장 호환을 포함합니다.

2026-09-21 실제 InputImages **20장**을 단일 요청으로 가져와 앨범의 정확한 사진 ID 20개와 원본 바이트를 확인했습니다. 1장 테스트 후 이어하기로 두 번째 사진까지 Reframe·캡처 두 장·JPEG 저장·편집 보존을 완료했습니다. JPEG는 각각 1440×1801/1,957,674바이트와 768×1022/612,048바이트이며 전체 디코딩·해시를 검증했습니다. 이후 별도 PhotoKit 검사에서도 두 사진의 `hasAdjustments=true`와 내보낸 편집 이미지의 해시 일치를 확인했습니다. 입력 파일 20개의 바이트도 그대로였습니다. **나머지 18장은 아직 처리하지 않았습니다.** 이 결과는 당시 InputImages 모드의 기록이며 새 Reframe 사본 모드의 전체 성공 검증을 뜻하지 않습니다.

두 번째 사진의 첫 시도는 생성 중 Photos의 전면 이탈로 중단됐습니다. 미완료 기록으로 초안을 정리하고 동일 사진을 다시 처리했으며, 같은 앨범을 유지했습니다. 이 실행에서 전체 가져오기 요청은 한 번, 원본 복귀 요청은 0번이었습니다. 기존 미완료 프리뷰 파일은 덮어쓰지 않고 재시도 결과에 `-002`를 붙였습니다.

기존 임시 서명에서 새 개발자 서명으로 전환한 직후에는 네 권한 재승인이 필요했습니다. 승인과 사진 테스트를 마친 뒤 빌드 캐시를 비워 **같은 인증서로 실제 재컴파일·재서명·앱 교체**를 수행했습니다. 인증서·팀·designated requirement가 같았고, 재시작 후 손쉬운 사용(이벤트 입력 포함)·화면 기록·사진 전체 접근·자동화 → 사진 권한이 모두 재승인 없이 유지됐습니다. 다른 Mac·다른 사진의 전체 배치 성공까지 검증한 것은 아닙니다.

### 이전 버전 검증 기록

0.1.9는 실제 사진에서 재현한 편집 버튼의 `AXPress -25205` 응답과 편집 화면의 선택적 `AXValue -25200` 조회 실패를 처리합니다. 필수 역할·활성 상태·창 좌표·트리 조회 오류는 계속 중단하며, 없는 속성을 추정해 버튼을 선택하지 않습니다. UI 요소를 해시만으로 동일하다고 판단하던 코드도 `CFEqual` 확인으로 수정했습니다.

2026-09-21 후속 JavaScript 수정 후, 가져오기·원본 검증을 통과한 **같은 사진 사본 한 장**으로 실제 편집 → 도구 → 프레임 재설정 → 좌하단 드래그 → 프리뷰 캡처 → 재생성 → 결과 캡처 → 저장 → JPEG 내보내기 → 원본 복귀를 완료했습니다. JPEG는 1440×1801, 1,956,061바이트였으며 전체 디코딩·SHA-256 검증을 통과했습니다. 복원 후 `hasAdjustments=false`이고 편집 전 이미지와 해시가 일치했습니다. 실행 결과 `manifest.status=complete`, 사진 결과 `status=complete`, 미완료 기록 제거를 확인했습니다. 새 사본을 추가로 가져오거나 앨범 전체를 실행하지는 않았습니다.

이번 후속 수정은 버튼 구분, 기본 구도·드래그 변화 확인, 완료 버튼의 실제 화면 전환 확인, UI 전환 중 사라진 요소(`AX_READ_FAILED ... -25202`)에 대한 최대 3회의 새 화면 조회를 포함합니다. 클릭·드래그·저장을 자동 재전송하지 않으며, 전면 이탈·다른 사진·창 변경·대화상자는 계속 중단합니다. 오프라인 검사 **146개**를 통과했습니다. 기존 0.1.9 도우미를 그대로 사용했고 재빌드나 권한 초기화는 하지 않았습니다.

아래는 이전 버전에서 당시 수행했던 검증 기록입니다.

0.1.8은 네 권한 요청에서 별도로 시스템 설정을 여는 동작을 제거하고 안내 문구를 수정했습니다. 전체 Swift 소스를 임시 앱으로 빌드·서명 검증했으며, 권한·설정 창 관련 기존 검사 7개를 통과했습니다. 실행 중인 설치 앱은 교체하지 않았고 실제 macOS 권한 요청 팝업의 재검증은 아직 수행하지 않았습니다. 이 변경을 적용하려면 도우미 종료 후 설정 커맨드로 다시 빌드합니다.

0.1.7에서는 로컬 실사진 테스트의 `show` 요청에서 `AppleScript -1700`이 발생한 것을 확인했습니다. 목록 참조만 풀어도 내부 앨범 조회에서 `-1728`이 남는 것을 실제 앱에서 확인한 뒤, 원시 선택 객체의 전체 사진 ID를 읽는 방식으로 수정했습니다. 수정된 앱을 빌드·서명하고, 기존에 가져온 같은 실사진의 `selection`·`albumItems`·`albums`·`show`가 정확한 ID를 반환하며 `selected:true`인 것을 확인했습니다. 새 사본은 만들지 않았습니다. Node.js 22.23.1의 **97개 오프라인 테스트**도 통과했습니다. 재빌드 후 화면 조작·화면 기록·사진 전체 접근 권한 재승인이 필요해, **편집·캡처·JPEG 저장·원본 복귀 전체 실행은 아직 완료하지 못했습니다.**

0.1.6은 검증한 파일을 통한 가져오기, 이전 도우미 실행 차단, 바이트·해시 불일치 상세 기록을 추가합니다. Node.js 22.23.1에서 **96개 테스트**를 통과했습니다. 메타데이터를 포함한 합성 JPEG의 임시 파일 바이트 보존, 파일·폴더 권한, 비동기 처리 중 파일 유지, 성공·오류 시 정리, 청크별 SHA 계산·시간초과·중복 콜백을 오프라인으로 검사했습니다. 전체 Swift 소스를 별도 임시 앱으로 컴파일하고 임시 서명을 검증했으며, 실행 중인 도우미는 교체하지 않았습니다. **사용자의 오류 파일로 실제 가져오기·편집을 재검증하지는 못했습니다.**

0.1.5 이후 JavaScript 수정에서는 사진 열기 요청 직후 Photos가 전면으로 전환되는 시간을 기다리도록 보완했습니다. 이 최초 전환 이후에 다른 앱으로 전환되면 기존처럼 즉시 중단합니다. 복사 이후 단계별 진행 표시와 `manifest.json`의 마지막 요청 기록도 추가했습니다. Node.js 22.23.1에서 **95개 테스트**를 통과했으며, 전면 전환 지연·시간초과·편집 중 전면 이탈을 포함합니다. 이 JavaScript 수정만 적용할 때는 도우미 재빌드가 필요하지 않습니다. 이후 사용자가 제공한 오류로 복사 후 SHA-256 검증에서 중단된 것이 확인되어, 별도로 0.1.6의 파일 가져오기 수정을 추가했습니다.

0.1.5는 권한별 요청·설정 열기, 현재 앱 위치 확인, 명시적 권한 초기화 후 재시작 기능을 추가합니다. 사진 앱 일부 요소에서 선택 속성인 `AXDescription`을 읽을 때 발생하는 `AX_READ_FAILED: AXDescription 조회 실패: -25200`도 기존 `AXSubrole`과 같이 해당 속성만 생략하도록 수정했습니다. 설명이 없으면 그 설명을 요구하는 버튼은 선택하지 않습니다. 역할·활성 상태·좌표·크기·화면 트리 조회 실패와 권한·통신 오류는 계속 중단합니다.

0.1.5의 빌드·서명 검증과 Node.js 22.23.1에서 **91개 테스트**를 통과했습니다. 실제 설정 창에서 네 권한 버튼과 초기화 안내가 표시되고, 화면 기록 설정 열기가 해당 시스템 설정 페이지로 이동하며, 실행 중 설정 커맨드로 창이 다시 열리는 것을 확인했습니다. 초기화 명령은 모의 실행으로 대상 제한·부분 실패·진행 중 작업 보호를 검증했습니다. 실제 권한 초기화·승인이나 실사진 1장 재실행은 수행하지 않았습니다.

0.1.4는 `InputImages/`를 기본 입력으로 사용하고, 새 작업 앨범에 복사한 사진을 정확한 ID로 처리하도록 구성합니다. **입력 가져오기부터 실제 Mac 사진 편집·JPEG 내보내기·원본 복귀까지의 전체 흐름은 아직 실사진으로 검증하지 않았습니다.**

0.1.4 도우미의 최종 빌드·서명 검증과 Node.js 22.22.3에서 **89개 테스트**를 통과했습니다. 입력 폴더 탐색·가져오기 식별 검증·앨범 반영 대기·중지와, 합성 JPEG/PNG/TIFF 원본·해시·가져오기 기록 검사를 포함합니다. 도우미 없이 파일 접근을 임시 프로젝트에만 제한한 상태에서도 기본 `plan`이 실행되는 것을 확인했습니다. 해당 도우미의 입력 폴더 기능 응답도 확인했으며 권한을 자동 부여하거나 실제 사진을 가져오지는 않았습니다.

오프라인 테스트는 기본 로직·처리 흐름과 Node 버전 검사·실행 파일의 Node 선택을 검사합니다. 다음 명령은 실제 사진 앱을 조작하지 않습니다. 빌드·오프라인 검증과 실사진 검증은 구분해야 합니다.

이전 버전에서 Node.js 22.23.1과 26.9.0, 보조 앱 통신, 합성 JPEG의 전체 디코딩·해시 검증, 만료 요청 차단, 설정 창 재열기를 확인했습니다. 이 결과는 새 입력 가져오기 기능의 실사진 검증을 뜻하지 않습니다. 지원 버전 검사는 Node.js 22.12.0 이상을 허용합니다.

### 0.3.0 앨범 사본 및 편집 전 조회 보완

**사진 사본 생성 기능은 도우미 재빌드가 필요합니다.** 보조 앱 종료 후 설정 커맨드를 실행하세요. 같은 서명 설정을 재사용하며 권한을 초기화하지 않습니다. `검사 중 사진이 변경되었습니다.` 오류에 한해 **편집 전** 같은 사진 ID·보기 화면을 다시 확인하고 최대 3회 전체 조회합니다. 계속 변하거나 다른 오류가 나면 중단하며, 편집 버튼·가져오기·내보내기·복원 요청을 재전송하지 않습니다. 실제 재현 기록에서는 세 번째 사진의 편집 전 조회가 실패했고 이후 같은 사진의 조회 두 번이 성공했습니다. 사진 데이터 손상이나 가져오기 실패로 단정하지 않습니다.


사본 생성은 PhotoKit의 원본 리소스 읽기와 단일 사진 생성 트랜잭션을 사용합니다. [Apple 원본 리소스 API](https://developer.apple.com/documentation/photos/phassetresourcemanager)와 [사진 생성 API](https://developer.apple.com/documentation/photos/phassetcreationrequest)를 사용하며 보관함 DB를 직접 수정하지 않습니다.
